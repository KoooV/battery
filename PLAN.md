# Battery Tray — план разработки

Приложение на Rust для Linux. Показывает в трее отдельную иконку с процентом заряда для каждой мыши и клавиатуры. Опрос устройств раз в 10 минут, одно уведомление при заряде 10%, автозапуск при входе в систему.

**Окружение:** niri (трей через Noctalia), GNOME (трей через расширение AppIndicator).
**Производители:** все, которые удастся реализовать. Logitech, Razer и остальные — отдельными бэкендами.

---

## Стек

| Задача | Крейт |
|---|---|
| D-Bus (UPower, OpenRazer) | `zbus` |
| Трей (StatusNotifierItem) | `ksni` |
| HID-устройства (Logitech HID++) | `hidapi` |
| Уведомления | `notify-rust` |
| Рисование иконки с процентом | `tiny-skia` (+ растровый шрифт или `fontdue`) |
| Таймер опроса | `std::thread` / `tokio` (что проще) |
| Логи | `tracing`, `tracing-subscriber` |
| Ошибки | `anyhow`, `thiserror` |

## Этап 0. Подготовка окружения

**Цель:** понять, что система видит, и подготовить проект.

- [x] Установить Rust через `rustup`, проверить `cargo --version`
- [x] Выполнить `upower -d`, сохранить вывод в `docs/upower-dump.txt`

- [x] Определить, какие устройства UPower уже видит, и какие не видит
- [x] Составить таблицу «устройство → источник данных» в `docs/devices.md`
- [x] Создать репозиторий: `cargo new battery-tray`, инициализировать git
- [x] Установить системные зависимости для сборки (`libdbus`, `pkg-config`, `libudev` — по необходимости)

**Итог этапа 0:** UPower видит только аккумулятор ноутбука; оба беспроводных
комплекта (мышь и клавиатура) — самодельные 2.4G-донглы `36b0:3002` и
`3554:f53c` без стандартной HID-страницы батареи, протокол не документирован.
Logitech и Razer отсутствуют. `libdbus` не понадобился: `zbus` и `notify-rust`
работают через чистый Rust. Подробности и ограничения — в `docs/devices.md`.

**Критерий готовности:** есть таблица, где для каждого устройства указан источник данных или пометка «не видно».

## Этап 2. Источник UPower

**Цель:** читать заряд всех устройств, которые UPower уже видит.

- [x] Подключиться к системной шине D-Bus через `zbus`
- [x] Вызвать `org.freedesktop.UPower.EnumerateDevices`
- [x] Для каждого устройства прочитать `Type`, `Model`, `Percentage`, `IsPresent`
- [x] Отфильтровать: оставить только мыши, клавиатуры и прочие периферийные устройства (исключить основной аккумулятор ноутбука, если он есть)
- [x] Реализовать `UpowerSource: BatterySource`
- [x] Вывести в консоль список устройств и уровни
- [x] Обработать отсутствие UPower и устройства, которое отключили во время работы
- [ ] Проверить критерий на железе, которое UPower видит (блокер: на машине
      разработки UPower не показывает ни одной мыши или клавиатуры, см.
      `docs/devices.md`)

**Критерий готовности:** консольный вывод показывает заряд мыши и клавиатуры, которые видит UPower.

**Состояние:** соединение, перечисление и фильтрация подтверждены запуском на
`upower` 1.91.5 (аккумулятор и адаптер отсеяны, список периферии пуст);
положительный сценарий — «устройство → заряд» — покрыт модульными тестами на
сохранённом ответе `GetAll` в `tests/fixtures/upower-getall.txt`. Живьём критерий
не проверен: подходящего устройства нет. Отсутствие UPower обрабатывается через
`SourceError::Unavailable`, исчезнувшее между `EnumerateDevices` и `GetAll`
устройство — через `SourceError::Read`; живьём эти ветки не воспроизводились.

zbus 6 не имеет блокирующего API, поэтому вызовы идут через `zbus::block_on`;
таймаут каждого вызова — 5 с, задаётся на соединении.

## Этап 5. Уведомления

**Цель:** одно предупреждение при заряде 10%.

- [ ] Реализовать отправку через `notify-rust` с текстом: название устройства и уровень
- [ ] Логика срабатывания: уведомление при переходе с выше 10% на 10% и ниже
- [ ] Повторное уведомление только после подзарядки выше 10% и нового падения
- [ ] Не отправлять уведомление при первом опросе, если заряд уже ниже порога, — иначе будет спам после перезапуска (решить, нужно ли это, и зафиксировать в решении)
- [ ] Проверить на устройстве с реально низким зарядом или через временно поднятый порог

**Критерий готовности:** уведомление приходит один раз при падении до 10% и не повторяется на следующих опросах.

Этапы идут по порядку: 0 → 1 → 2 → 3 → 4 → 5, после этого 6, 7, 8 в любом порядке. Этапы 9–11 в конце.

Минимально работающая версия готова после этапа 5 (UPower, трей, уведомления). Всё остальное добавляет поддержку устройств и удобство.
